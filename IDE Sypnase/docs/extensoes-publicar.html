Empacotar, versionar e publicar

Do pacote .sx local até a entrada no registro público, com assinatura, Release no GitHub e o fluxo automatizado que o assistente já deixa configurado.

revisado em 15/09/2026 leitura 8 min público: dev

O que é um pacote .sx

Um .sx é um ZIP da pasta da extensão com o manifesto na raiz, sem node_modules, .git, pacotes anteriores e arquivos de teste de desenvolvimento. A IDE calcula o SHA-256 do arquivo e esse hash vira a identidade daquela versão no registro: mudou um byte, mudou o hash, a instalação recusa.

Instalar um .sx passa pela mesma validação de manifesto de uma pasta de desenvolvimento, mais a checagem de hash e, quando houver, da assinatura.

Antes de empacotar

  1. Aumente version no manifesto seguindo semver: correção → patch, recurso → minor, quebra de compatibilidade → major.
  2. Registre a mudança em CHANGELOG.md na seção da nova versão. O registro mostra esse trecho na página da extensão.
  3. Confira engines.synapse: se você usou uma API nova, suba o mínimo.
  4. Rode os testes no Extension Development Host. O empacotador não bloqueia por teste falhando, mas o registro exibe o resultado da última execução.
  5. Preencha repository com a URL pública do GitHub e license.

Empacotar pela IDE

Extensões: Empacotar (.sx) pede a pasta (ou usa a única existente), valida, gera o arquivo e baixa. O nome segue <nome>-<versão>.sx e o console mostra o SHA-256 e os avisos encontrados (arquivos grandes, permissões amplas, ícone ausente).

Para distribuir sem registro, basta enviar o .sx: quem recebe usa Extensões: Instalar de arquivo (.sx).

Assinatura

Extensões assinadas recebem o selo Verificado. A chave é ECDSA P-256 gerada uma vez por publisher com Extensões: Gerar chave de assinatura do publisher; a parte privada fica só no seu navegador (IndexedDB) e a pública vai para o registro junto com a primeira publicação.

Faça backup Use Extensões: Exportar chave de assinatura e guarde o arquivo em lugar seguro. Perder a chave significa publicar as próximas versões sem selo até que uma rotação seja aprovada no registro.

Publicar no registro

Extensões: Publicar no registro faz tudo que o empacotamento faz e ainda prepara a entrada do registro:

  1. Verifica que publisher é igual ao dono do repositório (em minúsculas) e que a versão é maior que a última publicada.
  2. Gera dist-sx/<nome>.registry.json com id, versões, hash, assinatura, tag e URL do asset.
  3. Baixa o .sx e copia o JSON para a área de transferência.
  4. Abre o GitHub com o arquivo do registro já pré-preenchido em registry/<publisher>/<nome>.json.

Você então cria a Release vX.Y.Z no seu repositório anexando o .sx, e abre o PR no registro. A Action do registro baixa o asset, confere o hash, a assinatura e o semver, e faz o merge sozinha quando tudo bate.

Automatizar com GitHub Actions

O assistente de nova extensão gera .github/workflows/release.yml. Com ele o fluxo vira apenas subir a versão, commitar, criar a tag: 

git commit -am "v1.2.0"
git tag v1.2.0
git push --tags

O workflow:

  • falha se a tag não bater com version do manifesto;
  • gera o .sx excluindo .git, .github, node_modules e pacotes anteriores;
  • escreve SHA256SUMS.txt;
  • cria a Release com notas automáticas e anexa os dois arquivos.

Depois disso, só falta o PR no registro, que a IDE prepara com um clique. Se você já publicou antes, o PR é uma linha nova na lista de versões.

Atualizações e rollback

Quem instalou pelo registro recebe aviso de nova versão na tela de extensões e pode atualizar com um clique. A IDE guarda o pacote anterior e oferece Extensões: Voltar para a versão anterior se a nova quebrar algo.

Para retirar uma versão problemática do ar, abra um PR no registro marcando-a com "yanked": true; instalações existentes continuam, novas passam a receber a versão anterior.
